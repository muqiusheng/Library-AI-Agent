# 项目迭代实操指南

本指南说明如何把一个新想法变成可评审、可发布、可追溯的项目版本。Git 命令默认在仓库根目录的 Windows PowerShell 执行；示例 Issue 编号、分支名和版本号均需替换。分支规则及冲突处理见 [协作指南](../CONTRIBUTING.md)，环境安装见 [部署指南](../DEPLOYMENT.md)。

## 1. 先完成主线交接，再开始常规迭代

2026-10-20 已确认，远程默认分支是 `chore/repository-standardization`。这是本次交付的过渡状态，尚不能仅凭分支名判断 `main` 已包含完整系统。

维护者完成以下事项后，再按后续章节从 `main` 开始开发：

1. 提交需要保留的协作与迭代文档，推送到交付分支。
2. 创建 `chore/repository-standardization` → `main` 的 PR，检查完整系统差异并执行验证。
3. 通过评审后合并，确认 `main` 能构建、运行，文档和配置示例齐全。
4. 在 GitHub 仓库设置中将默认分支改为 `main`，配置主线保护，并核对部署使用的分支或标签。
5. 团队成员拉取并更新默认分支引用：

```powershell
git status
git fetch --prune origin
git remote set-head origin -a
git switch main
git pull --ff-only origin main
```

执行切换前处理未提交修改。如果本地 `main` 与远程分叉，停止并按协作指南核对提交，不能用强制重置跳过检查。若本地没有 `main`，使用 `git switch --track origin/main`。

交接完成后，每次迭代都创建新任务分支，不再把新功能持续堆进本次交付分支。集成代码与发布上线是两个步骤，合并 PR 不表示生产环境已经更新。

## 2. 规划一次迭代

一次迭代围绕一个可以验证的目标，例如“让学生为学习路径的每个阶段设置截止日期”。这是后续开发的示例需求，不代表仓库已实现此功能。

先在 GitHub 创建 Issue；没有使用 Issue 时，也应在 PR 描述中记录以下内容：

```markdown
标题：学习路径支持阶段截止日期

背景：学生需要知道每个学习阶段何时完成。
本次范围：设置、修改、清除阶段截止日期，并在路径页面显示。
不在本次范围：短信、邮件、自动催办和日历同步。
验收条件：
- 路径所有者可设置、修改、清除截止日期，刷新后仍能正确显示。
- 其他用户不能读取或修改不属于自己的路径数据。
- 非法日期返回明确错误；旧路径没有截止日期时仍可访问。
- 前后端约定日期含义和格式，不出现时区导致的日期偏移。
影响：学习路径页面、API、数据表及相关测试。
负责人：填写实际成员；评审人：填写实际成员。
依赖与风险：需数据库迁移，旧记录必须兼容。
验证计划：接口测试、权限测试、旧数据升级与页面人工验收。
```

把“优化一下”“做得更智能”改成可检查的行为。性能目标应记录测试环境、基线、样本及期望值；推荐质量目标应固定评测样本和判定方式，避免只看一条聊天结果。

任务优先级可依次考虑：线上故障或安全缺陷、阻塞主要流程的问题、明确的用户需求、内部结构优化。不要为凑版本号把无关工作塞进同一个 PR。

复杂需求拆为可独立评审的任务，每个任务明确输入、输出、负责人和依赖。对上述示例，可按“兼容的数据/API → 页面交互 → 综合验收”拆分；前后端同时开发时先约定接口。未完成的功能不要提前开放入口。多人协作优先各自使用任务分支，共享分支的同步方式见协作指南。

## 3. 从最新主线创建任务分支

以下流程以首次主线交接已经完成为前提：

```powershell
git status
git fetch --prune origin
git switch main
git pull --ff-only origin main
git switch -c feat/123-stage-deadline

uv sync --locked
Push-Location frontend
try { npm ci } finally { Pop-Location }
```

新功能用 `feat/*`，缺陷用 `fix/*`，结构重构用 `refactor/*`，纯文档用 `docs/*`。不为每个迭代新建 `main04`、`main05`，也不把个人或开发工具名称写进分支前缀。

依赖同步后检查每个命令结果，失败时先修复环境。已有 `.env`、`.env.home` 不要覆盖，也不要把生产数据复制到开发环境。原生开发、Docker 启动方式及数据库地址按部署指南配置，开发与生产使用不同数据环境。

## 4. 先设计变化，再修改对应层

| 改动内容 | 优先检查的现有位置 | 需要同步考虑 |
|---|---|---|
| 页面和交互 | `frontend/src/pages/`、`frontend/src/components/` | 加载、空数据、失败、权限与移动端状态 |
| 前端请求和类型 | `frontend/src/api/`、`frontend/src/types/` | 字段名称、可空性、错误响应和类型兼容 |
| HTTP 接口 | `app/api/v1/` | `/api/v1` 契约、认证、参数校验与错误码 |
| 请求与响应结构 | `app/schemas/` | 字段类型、校验、默认值与响应兼容 |
| 业务规则 | `app/services/` | 规则边界、事务、异常路径与可测试性 |
| 数据读写 | `app/repositories/`、`app/db/models/` | 查询、索引、约束与用户数据隔离 |
| 数据库结构 | `app/db/migrations/versions/` | 升级脚本、已有数据、回退或补救方案 |
| 推荐与模型能力 | `app/services/recommendation_service.py`、`app/integrations/`、`app/pipelines/` | 真实馆藏约束、降级、延迟与模型费用 |
| 配置和部署 | `app/core/`、配置示例、Compose 文件 | 默认值、必填项、密钥、环境与文档 |

业务逻辑放在服务层，避免堆在页面或路由中。变更 API 时同步前端 API 客户端和类型；新增字段尽量先做兼容扩展，不直接删除旧客户端仍使用的字段。

对“阶段截止日期”示例，开发前先决定：字段保存日期还是时间点、是否可空、清除字段如何表达、错误如何返回、谁有权限修改。然后同时维护模型、迁移、业务校验、接口、前端类型和页面，而不是只给页面加一个日期输入框。

### 数据库变更

只在隔离的开发数据库执行，先确认连接配置。模型修改后生成候选迁移，再人工审查；自动生成不能替代对改名、数据回填和约束的判断：

```powershell
uv run --locked alembic current
uv run --locked alembic heads
uv run --locked alembic revision --autogenerate -m "add stage deadline"
# 检查新迁移的 upgrade / downgrade，以及是否误删表、列或索引
uv run --locked alembic upgrade head
```

迁移文件和模型一起提交，不只改本地数据库。已被他人或线上使用的迁移不能直接改写，应追加修复迁移。多人并行产生多个 head 时，需要协调迁移依赖，评审后再解决分叉。

验收既要覆盖新建空库，也要覆盖带旧数据的数据库升级。新增必填列通常先允许为空或提供合理回填，等数据完成迁移、旧代码不再依赖后再收紧约束。`downgrade` 是否真的能恢复结构与数据必须单独验证，不能默认删除新字段就等于安全回滚。

### 推荐、模型及知识库变更

固定一组匿名化场景，例如零基础、指定课程、仅可借、排除已读、无结果和模型不可用；比较修改前后的候选书目、约束遵守、解释是否引用真实数据、响应时间和调用成本。模型输出有波动时重复测试并记录模型与参数。

更换嵌入模型、分块方式或向量维度时，确认是否需要重建 Chroma 索引；用新数据版本验证，记录如何切换及回退。不要直接覆盖线上索引后才检查结果。馆藏或规则变化应能追溯数据版本，不把数据库和运行时向量文件作为代码提交。

### 依赖变更

普通开发使用锁文件安装。确有需要新增 Python 依赖时使用 `uv add <包名>`（开发依赖加 `--dev`），同步评审 `pyproject.toml` 和 `uv.lock`；前端用 `npm install <包名>`，同步评审 `package.json` 和 `package-lock.json`。这些是按需操作示例，不是每次迭代都执行的升级命令。

## 5. 小步提交，及时同步

实现一个完整、可说明的变化后，检查并选择性暂存。下面为示例路径，根据实际改动替换：

```powershell
git diff
git add app/services/learning_path_service.py frontend/src/api/learningPaths.ts
# 再选择性加入本任务的模型、迁移、页面及测试文件
git diff --cached
git commit -m "feat(learning-path): support stage deadlines"
git push -u origin feat/123-stage-deadline
```

定期 `git fetch origin`，在任务分支用 `git merge origin/main` 同步主线，然后重新验证受影响部分。同一个任务第二天继续做时，回到原任务分支并同步其上游即可，不必每天新建分支。任务完成且合并后，新需求再从最新 `main` 建分支。

推送后尽早开 Draft PR，写明未完成事项；不等全部写完才让协作者看到接口变化。不要混入无关格式化、全库依赖升级或其他功能。如果临时需要修线上故障，先保存当前工作，再按第 9 节创建独立修复分支。

## 6. 验证：从局部到完整链路

开发中先运行与改动相关的测试；行为变化应补对应测试，缺陷修复优先保留复现用例。例如学习路径权限或业务逻辑变动，需要覆盖本人、其他用户、非法输入和不存在的资源。

准备评审时，代码变更执行完整检查。下面显式检查退出码，某一步失败就停止，避免把后续命令的成功误认为全部通过：

```powershell
uv run --locked pytest app/tests -q
if ($LASTEXITCODE -ne 0) { throw '后端测试失败' }
uv run --locked ruff check app
if ($LASTEXITCODE -ne 0) { throw 'Ruff 检查失败' }
Push-Location frontend
try {
    npm run test
    if ($LASTEXITCODE -ne 0) { throw '前端测试失败' }
    npm run build
    if ($LASTEXITCODE -ne 0) { throw '前端类型检查或构建失败' }
} finally { Pop-Location }
git diff --check
if ($LASTEXITCODE -ne 0) { throw '差异格式检查失败' }
```

还要启动隔离的测试环境，实际走通“登录 → 画像 → 推荐 → 反馈 → 学习路径”，按改动范围检查管理端导入、标签与索引。页面变化需人工检查交互；新增权限必须测试无登录、普通学生和管理员边界。测试 API Key 关闭或模型失败时的降级，不能只测模型正常返回。

在 PR 记录执行命令、结果、人工操作步骤及未覆盖内容。纯文档变更验证链接、路径、命令和格式即可。项目现有 `scripts/verify.ps1` 对原生命令的退出码检查不完整，使用时需核对各项输出；末尾成功提示不能替代结果检查。

## 7. 评审、合并与完成标准

PR 设置 `base: main`、`compare: 本次任务分支`，使用 [PR 模板](../.github/pull_request_template.md)。说明需求与验收条件、实现后的行为、配置/API/数据库影响、验证证据和发布回滚步骤。前端变化附截图，关联 Issue 可写 `Closes #123`。

任务进入“可合并”状态前应满足：

- 验收条件已逐条验证，必要测试通过，失败和权限边界已检查。
- 数据库迁移及旧数据兼容性已验证，配置示例和文档已同步。
- 已检查暂存和 PR 差异，没有密钥、用户信息或运行时数据。
- 评审意见已处理，多人团队至少有一位其他成员批准。

独立维护时保留 PR 和自查记录，便于回溯；若仓库规则要求其他成员批准，仍需满足该规则。维护者确认最终提交的验证结果后执行 Squash merge。若多个任务组成一个迭代，每个任务各自合并，不要求一个迭代只有一个巨大 PR。

合并后切回 `main`，执行 `git pull --ff-only origin main`，检查集成结果；再清理任务分支，具体见协作指南。PR 已合并可关闭开发任务，但版本是否上线、线上验收是否通过，要在发布记录中另行跟踪。

## 8. 版本与发布

### 确定版本和发布范围

发布只包含已合并、验证完成的改动。建立一条发布记录，列出目标提交、关联 PR、功能与修复、配置与迁移、部署负责人、验证结果和上一可用版本。

版本采用 `v主版本.次版本.修订版本`：兼容性修复增加修订版本，兼容的新能力增加次版本，不兼容的契约或升级要求增加主版本。先统一项目版本基线；当前 `pyproject.toml` 为 `0.1.0`、前端为 `2.0.0`，历史提交还出现其他版本表达，不能直接据此认定整套系统的正式版本。

维护者选定统一基线后，在发布 PR 同步需要对外展示的版本信息、锁文件及发布说明。版本号与 Git 标签一致性应纳入检查；不要只改一个文件或只根据分支名判断上线版本。

以下 `v2.1.0` 仅示例，确认版本号未占用、工作区干净且 `HEAD` 是已验证的目标主线提交后才执行：

```powershell
git switch main
git pull --ff-only origin main
git status --short
git log -1 --oneline
git tag -a v2.1.0 -m "BookPath AI v2.1.0"
git push origin v2.1.0
```

本地脏工作区不会进入标签，版本文件和说明必须先提交并合入主线。标签只推送这一次指定的版本，不使用 `--tags` 批量发布本地标签；发布后不移动或覆盖已有版本标签。

### 部署与上线验收

先在独立测试环境按 [部署指南](../DEPLOYMENT.md) 演练升级和恢复，再安排生产发布窗口。部署使用干净、专用的检出目录，核对标签对应的提交，保存上一版本标签、镜像或可重建条件，以及当前配置和数据库迁移版本。

1. 发布前备份 PostgreSQL、上传目录及需要保留的向量索引，记录备份位置和恢复验证结果。
2. 检查新增环境变量、数据迁移、索引重建、磁盘空间和预计停机影响。
3. 检出目标发布标签，在正确的环境配置下构建并启动，随后检查迁移、容器和日志。
4. 验证健康检查、登录权限、真实馆藏推荐、学习路径及本次验收条件，记录结果。
5. 观察错误率、响应时间和模型调用异常；通过后将发布记录标为完成，保留回滚材料。

项目家庭服务器栈提供下列脚本，使用前核对参数和部署环境：

| 脚本 | 用途及限制 |
|---|---|
| `scripts/home-backup.ps1` | 备份数据库和上传目录；需传入实际 Docker 路径，当前脚本未归档 Chroma 卷 |
| `scripts/home-smoke-test.ps1` | 检查页面、健康和匿名鉴权；`-BaseUrl` 指向目标环境，不代替业务验收 |
| `scripts/home-release-check.ps1` | 现有家庭栈检查含固定馆藏数量及版本标识，须先核对是否适用；不包含前端 Vitest |
| `scripts/home-restore-drill.ps1` | 恢复演练；使用前阅读脚本并确认隔离环境 |
| `scripts/home-restore.ps1` | 替换生产数据库，属于恢复操作；不能当作普通重启使用 |

`Dockerfile` 的后端启动命令会先运行 `alembic upgrade head`，因此重建启动可能立刻修改数据库，备份及迁移评审必须在前。家庭栈的构建更新命令为 `docker compose -f docker-compose.home.yml up -d --build`，只在确认上述发布条件后执行。开发栈使用 `docker-compose.yml`；两套环境和数据卷不要混用。

不要使用 `docker compose down -v` 作为常规更新步骤，它会删除所选栈的数据卷。当前脚本也不构成通用的无人值守发布流水线，CI 和自动发布尚需另行建设。

## 9. 发布失败、紧急修复和回滚

先记录故障版本、影响范围和发生时间。权限失效、主要业务不可用或数据异常，应暂停继续放量或写入，按预案恢复，而不是直接在生产机器上临时改代码后忘记回流仓库。

- **只涉及应用代码且数据库兼容**：部署上一可用标签或镜像，核对配置并重新验收；另建修复任务。
- **包含结构、数据或索引变化**：先检查旧代码兼容性，选择向前修复、已演练的逆向迁移或备份恢复。恢复备份会丢失备份后的数据，必须评估并记录，不能仅回退 Git 就结束。
- **需要撤回主线中的改动**：从最新 `main` 建 `fix/*` 分支，用 `git revert <实际合并提交>` 形成可评审的撤回提交，经验证和 PR 后合并。Squash PR 对应一个提交；普通 merge commit 的撤回需要明确主线父提交，不能直接套用同一条命令。

已发布版本落后于主线时，从线上实际标签创建紧急修复分支，例如 `git switch -c hotfix/125-deadline-validation v2.1.0`。完成最小修复、测试和评审，安排补丁版本；同时通过 PR 将修复带回 `main`。不要把主线上尚未准备发布的其他功能一起带入线上补丁。

如果线上已运行最新主线，则直接从更新后的 `main` 创建 `hotfix/*` 并按正常 PR 流程处理。无论哪种方式，都记录修复在哪些版本生效，不依赖分支名称推断。

## 10. 一次迭代的结束与下一次开始

上线后确认验收结果，整理遗留问题和实际反馈，把未完成事项重新建立 Issue，不用“已合并”掩盖尚未上线或未验收的状态。记录本次主要风险、发现缺陷的原因，以及下一次最有价值的改进。

下次继续同一项目时，先阅读发布记录和未完成 Issue，再拉取最新 `main`、新建任务分支，重复上述流程。可以向开发协作者提供这样的任务说明：

```text
目标：为学习路径阶段增加可选截止日期。
基线：已完成交接的最新 main。
分支：feat/123-stage-deadline。
范围：API、数据库迁移、前端设置与展示；不做外部消息提醒。
验收：所有者可修改、他人无权修改、非法日期报错、旧数据兼容。
交付：代码、测试、迁移、文档、实际验证结果及 PR 描述。
```
